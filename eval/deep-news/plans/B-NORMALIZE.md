# B：从查询文本分离时间要求

## 任务与边界

检验“日期/时间指令混在语义查询中，是否影响主题检索”。开始前阅读 [统一契约](README.md)。你只写 `experiments/b_normalize/`，其他 agent 正在实现公共框架与 C/D，不得修改他们的文件。

B **只改送给 zg 的查询文本**：仍搜索全部 Deep News，单次 limit=100，保持原始文章排名。不按解析出的窗口过滤，不按日期加分，不拆分多次检索。

采用确定性规则解析，不调用 LLM，不读取正文、金标或固定查询映射。这使 B 对 A 的变化容易归因；更强的语言理解属于后续版本。

## 1. 文件与接口

```text
b_normalize/
  strategy.py       # normalize(query, as_of) -> QueryPlan
                    # search(request, runtime) -> SearchResult
  test_normalize.py
  test_strategy.py
  README.md
  RESULTS.md
```

`normalize` 是 C/D 的唯一公共依赖，输入只有 query 和 as_of。输出严格使用统一 QueryPlan。其实现不得依赖 A runtime；可先用字典与纯函数完成。

## 2. 解析步骤

1. 保存原字符串，按文本 span 提取时间短语，记录 rule 和原始起止位置。内部可规范空格，但 trace 坐标始终映射原文。
2. 先识别显式“不限发布时间”，再识别多阶段表达、明确起止日期、月份区间、单月、截至日与软偏好。若互相矛盾则 ambiguous，不按优先级强行覆盖。
3. 从已识别的 spans 构造日期条件，再删除这些 span 及它们直接附带的“只找/查找/发布的”等时间模板文字。
4. 保留主题、产品名、机制词、否定词和限定条件，规范重复空格/标点。不能增加原文没有的主题同义词、文章标题或专名。
5. 删除后为空或只剩“文章/分析”等泛词，标记 unsupported，并回退原查询。
6. 返回 QueryPlan。`status!=ok` 时 topical_query=original_query、mode=none、window=null、stages=[]，保留警告与已识别 trace。

“不限发布时间”题为了固定控制，v1 完全保留原查询，mode=none。无时间信号的查询也原样保留。

## 3. v1 必须支持的语法

| 表达 | 规则 |
|---|---|
| `2026 年 9 月 1 日至 15 日` | 同月继承年/月，闭区间 9/1–9/15 |
| `2026 年 8 月 15 日至 9 月 15 日` | 后端继承年，跨月区间 |
| `2026 年四月`、`2026 年六月至七月` | 月初到月末，使用 calendar 计算，不写死 30 天 |
| `截至 2026 年 9 月 15 日` | 参考日校验；当前数据中应等于 request.as_of，不等时报告 unsupported，避免假装支持历史知识回测 |
| `优先近两个月` | prefer_recent，按两个日历月回退，9/15→7/15；月末不存在则取目标月末 |
| `不限发布时间` | none，原样查询 |
| `六月的…、七月的…、八月的…` | 按顺序生成阶段；无年份从 as_of 推断不晚于参考日的对应年份；跨年歧义则 ambiguous |
| `六月到七月的…、八月的…、九月的…` | 第一个阶段为月份区间，不拆成两个阶段 |

中文月数至少支持一至十二，日数支持本题集数字；对未支持的复杂口语日期应明确 fallback。不要承诺覆盖所有中文时间表达。

若用户仅说“最近”而无可确定的窗口，v1 标记 ambiguous 并原样搜索，不私自设 30 天。若只有“截至日”但没有时间偏好，保留可确定的主题，mode=none，并记录未应用日期范围。

对于演进题：从冒号或明确引导语前提取共享主题；每阶段 query = 共享主题 + 该阶段去时间后的描述。顶层 topical_query = 共享主题 + 所有阶段描述，仍只检索一次。例如 MCP 演进题的 B 查询应包含确定性编排、工具中途问人、云端 agent 身份，但不含六/七/八月的时间词。

## 4. 示例（测试预期，不是硬编码映射）

```text
输入：只找 2026 年六月发布的 MCP 协议演进分析，关注自动执行、用户参与和授权边界。
输出主题：MCP 协议演进分析，关注自动执行、用户参与和授权边界。
mode=window；2026-06-01..2026-06-30
B 实际行为：仍对全体文章搜索这个主题。
```

```text
输入：GPT-4 的上下文窗口机制是什么？
输出：原样保留；mode=none。
```

测试中换成未出现在题集的主题，比如数据库备份与照片整理，仍应产生相同的时间结构；不能只通过这 30 句。

## 5. 策略执行与回退

`search` 调 normalize，再单次 runtime.retrieve(topical_query, route, 100, None)。结果保持原顺序，返回 plan 和完整候选。

解析失败与检索失败分开：前者可按上述策略 fallback，记录 fallback=true；后者仍是运行错误，不能当作解析回退后再加一次检索。B 的检索预算不能超过 A。

A 尚未完成时，用 fake runtime 断言调用参数、次数、顺序和预算即可。真实 B vs A 必须等两者在同一运行框架下完成。

## 6. 验证与对照

单元测试覆盖：跨月、二月/闰年、月末回退、数字/中文月、继承年/月、日期倒置、冲突条件、阶段区间、产品版本号、否定句、不限日期、空主题、unsupported 回退。

集成测试：不读取 gold；任何 query id 重命名都不改变检索；mode=window 也不设置 allowed_paths；所有查询只有一次调用；原理题与 A 查询一致。

全量 B vs A 报告：

- 30 条原查询、topical_query、解析模式和 warnings 清单。
- 解析窗口与评测端 time 的一致率；stages 的边界数量与日期单独人工复核。这个对照只在评分端做。
- 每类内容 Primary、Task、WindowPrimary、CandidateTask 的差值及 win/tie/loss。
- 若 B 改善，暂只归因于查询规范化；尚未证明时间筛选或重排有效。
- fallback 题纳入全部平均，另列比例，不能只报告能解析的题。
